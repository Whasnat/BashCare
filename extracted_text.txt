Business &amp; Product Requirements Document (PRD) Project:  BashaCare (Enterprise Tenant Management SaaS Platform)  Backend Architecture:  Pure Local PostgreSQL Database Engine + Node.js (Express/Fastify) Backend  Frontend Framework:  React.js (Single Page Application architecture)  Database Strategy:  Relational Multi-Tenancy via PostgreSQL Row-Level Security (RLS) &amp; Local Session Variables 1. Introduction &amp; Strategic Vision 1.1 Document Objective This document outlines the operational, structural, and security architecture for BashaCare. By migrating to a completely local PostgreSQL instance, the platform prioritizes structural integrity, relational querying power, and localized hardware execution speed over cloud-based backend-as-a-service solutions. This blueprint dictates exact data structures, programmatic triggers, and constraints required to build the backend. 1.2 Core Business Goals Flawless Data Isolation:  Enforce data multi-tenancy at the database level using PostgreSQL Row-Level Security (RLS). This prevents any accidental data leaks between landlords. Accounting Rigor:  Implement an append-only relational line-item transaction ledger. This tracks all payments, partial settlements, and carried-forward balances. Automated Utility Workflows:  Calculate variable billing cycles using delta-meter equations. These are processed directly via relational database triggers. Omni-Channel Payments:  Support diverse financial reconciliation, including automated MFS merchant gateways, manual MFS transfers, bank transfers, and cash payments, alongside high-deliverability messaging paths (WhatsApp/SMS). 2. Relational Multi-Tenancy &amp; Database Security Instead of building custom data-filtering layers in your application code, BashaCare handles multi-tenancy natively inside the database using PostgreSQL Row-Level Security (RLS). Since we are bypassing third-party auth for now, this will rely on database session variables. 2.1 Local Session RLS Architecture Every table inside the database includes a  landlord_id  foreign key. When a landlord or their building staff accesses the system, the Node.js backend injects their unique identifier into a local database connection context. PostgreSQL evaluates this ID against custom security policies before returning a single row of data. IDE Implementation Directive:  The backend must execute  SET LOCAL app.current_landlord_id = 'uuid'; . This must occur at the start of every transaction pool request to pass the context to the database. 3. User Roles &amp; Granular Access Control The platform relies on structured application roles to define data access boundaries. 3.1 System Admin (SaaS Operator) Access Level:  Bypasses standard RLS filters via a dedicated admin portal. Core Functions:  Approves landlord registrations, monitors cross-platform transactional volumes, and flags fraudulent accounts. 3.2 Landlord / Building Owner Access Level:  Full CRUD capabilities across all records assigned to their  landlord_id . Core Functions:  Modifies property structures, views legal leases, and monitors comprehensive financial health dashboards. Configures payment collection methods, whether utilizing official MFS merchant gateway keys or personal MFS/bank routing information. 3.3 Property Manager / Building Staff Access Level:  Restricted read/write access defined by granular database functions. Core Functions:  Logs monthly utility meter numbers, updates basic tenant contact cards, and logs direct cash payments from tenants. They cannot view the landlord's overall financial analytics dashboards or adjust payout credentials. 3.4 Tenant Access Level:  Isolated read-only access to their specific personal rows (Invoices, Leases, and Receipts). Core Functions:  Views current outstanding debts and triggers real-time mobile wallet checkouts. Submits transaction IDs for manual P2P transfers or bank deposits. 4. Omni-Channel Payment Architecture To accommodate varying landlord business scales, BashaCare splits payment processing into automated and manual verification tracks. 4.1 Payment Configuration Tiers MFS Merchant Tier (Automated):  Landlords with official bKash, Nagad, or Rocket APIs can enable automated web-checkout overlays. MFS Personal Tier (Manual):  Landlords utilizing regular user accounts can display their mobile numbers to tenants for standard &quot;Send Money&quot; transfers. Bank Transfer (Manual):  Landlords can provide bank routing details for direct deposits. 4.2 Processing Workflows MFS Merchant Checkout:  The React frontend interfaces directly with the local Node.js backend to initialize secure bKash, Nagad, or Rocket web-checkout windows. When a payment finishes successfully, a secure webhook payload hits your backend to instantly clear the ledger balance. MFS Personal &amp; Bank Transfers:  Tenants manually send funds via their preferred app or bank portal. They then submit the Transaction ID (TrxID) or deposit slip reference to the BashaCare portal. The invoice status updates to PENDING_VERIFICATION until the landlord manually approves the ledger clearing. Cash Payments:  A physical transaction where property staff enter the received amount into the system, which immediately clears the corresponding ledger balance. 5. Architectural Feature Breakdown (For IDE Ingestion) This section details exactly how the code works and the constraints required to prevent bugs at the database level. This relational structure eliminates duplicate data entries. It uses standard foreign key constraints to ensure that deleting a property automatically blocks orphaned units, maintaining absolute data consistency. 5.1 Property &amp; Profile Subsystem landlord_profiles  Table:  Stores  company_name  alongside configurable payment routing data (e.g.,  bkash_merchant_key ,  nagad_personal_number ,  bank_routing_number ). properties  Table:  Links to landlords via  landlord_id  (ON DELETE CASCADE) and stores  name  and  address . units  Table:  Defines individual apartments. Links to  property_id . Contains a  unit_number  and a  status  strictly enforced by an ENUM:  VACANT ,  OCCUPIED , or  MAINTENANCE . tenant_profiles  Table:  Captures  full_name , a unique  phone_number , and an  encrypted_national_id . 5.2 Leases &amp; Ledger Engine leases  Table:  The contractual bridge. Requires strict  NUMERIC(12, 2)  types for  base_rent  and  security_deposit  to avoid float precision bugs. Contains  start_date  and  end_date , along with a boolean  is_active  flag. ledger_invoices  Table:  The financial core. Tracks  amount_due  and  amount_paid . Uses an ENUM for  status :  UNPAID ,  PENDING_VERIFICATION ,  PARTIALLY_PAID ,  PAID , or  OVERDUE . 6. Functional Deep-Dive &amp; Execution Logic 6.1 The Double-Entry Ledger Logic To prevent loose math or broken balance statements, payments are treated as discrete transactions applied across an invoice's specific line-items using a strict database order of operations. When a tenant submits a partial payment via a mobile wallet, a PostgreSQL database transaction routes the money in this exact priority sequence: Accumulated Late Fees &amp; Penalties. Outstanding Utility Debts (Calculated via  utility_meter_logs ). Base Rental Fees. IDE Implementation Directive:  The backend must execute this payment allocation inside a standard SQL database transaction ( BEGIN TRANSACTION ... COMMIT ). If a payment fails or cuts off midway, the entire operation rolls back immediately. 6.2 Automated Utility Calculations (Native Triggers) Instead of relying on manual entry math, variable billing is calculated via native database triggers. Execution Steps for the Trigger: Pulls the new  meter_reading  from  utility_meter_logs . Fetches the previous highest  meter_reading  timestamp record for that specific  unit_id . Subtracts the values, multiplies the difference by the landlord's configured utility tariff tier, and appends the final calculated charge straight onto the tenant's upcoming  ledger_invoice . 6.3 Messaging Flow The system relies on a unified communication layout. When a new invoice generates, it calls a messaging function: Step 1:  Attempt Official Meta WhatsApp Template-Based Transaction API. Step 2:  On Success, exit pipeline. Step 3:  On Failure, execute Regional SMS (e.g., SSL Wireless API). 7. Advanced Edge Cases 7.1 Lease Transitions &amp; Tenant Swaps The Problem:  A tenant moves out early, or room keys are handed off to another person mid-month, risking overlapping billing histories. The Solution:  The database applies a system constraint trigger. A  unit_id  can never be linked to more than one active leases record tracking the same calendar date. Activating a new lease automatically updates the previous lease entry to  is_active = FALSE  and logs a historical termination timestamp. 7.2 Mid-Month Rent Adjustments The Problem:  The landlord agrees to apply a temporary discount or charge an extra repair fee right in the middle of an active monthly cycle. The Solution:  Landlords append a standalone balance adjustment row into the database, linked directly to the  ledger_invoices  reference ID. The system recalculates the absolute amount due on the fly using a SQL view aggregation whenever the tenant opens their billing screen. IDE Implementation Directive:  Create a PostgreSQL VIEW using the logic:  SELECT (base_rent + utility_charges + manual_adjustments) AS total_calculated_due; .
